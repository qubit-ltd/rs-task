# Qubit Task: Typed Task Service Design

[中文设计文档](task_execution_service_design.md)

This design targets `qubit-task` 0.11. Open the typed SQLite store with `SqliteTaskStore::open`; typed schema versions 4 through 7 migrate transactionally in place to version 8. Legacy UUID schemas are rejected without modification. See the [migration guide](migration.md) for upgrade steps.

This document describes the current typed task API. The former byte-oriented request, exact `(task_type, handler_version)` routing, local-closure submission, and legacy service builder are historical implementation details and are not the public contract.

## Model and routing

Each task has a stable `TaskId` wrapping `rs-id::Id`. The application injects an `IdGenerator` that must produce IDs unique across process restarts; Snowflake-style generators need distinct node IDs across processes and suitable clock configuration.

The service keeps routing, classification, and payload identity separate:

- `kind_id` selects a registered handler.
- `category` is an application query filter and does not affect routing.
- `Payload<T>` binds a value to `type_id`, `schema_version`, and `codec_id`.

A handler registered for a `kind_id` accepts one payload `type_id` and declares the schema versions it supports. The codec registry maps bytes codecs independently; a codec may serve multiple schema versions. Encoding validates the typed request and stores an `EncodedPayload` with its identity and bytes. Decoding and handler dispatch occur after acceptance when the task starts.

## Service and store

`TaskExecutionServiceBuilder` receives a typed `TaskStore`, byte codec registry, and ID generator. `capacity(ResourceCapacity)` configures the local engine's reservation budgets. The builder owns a `TypedTaskHandlerRegistry`; registrations are fixed when the service is built. The service writes accepted task data through the store and returns payload-free `TaskSummary` values for status reads and history pages.

Memory and SQLite stores implement the same typed store contract. SQLite uses its typed numeric-ID schema; an incompatible legacy UUID schema is rejected with a diagnostic rather than silently reinterpreted. Store ownership fences concurrent service instances, and recovery resumes retained queued work after acquiring ownership. A cleanup worker is started before owner acquisition. If the `build()` future is cancelled after acquisition, its armed guard queues release on that worker. Release is eventual, so an immediate replacement build can briefly conflict with the previous owner.

One scheduler scans queued summaries in bounded pages and starts handlers only while a running slot is available. `max_running_tasks` defaults to available parallelism; `scan_page_size` defaults to 128 and is capped at 256. Retry deadlines are persisted in SQLite schema version 8 and observed across restarts. Positive delays are rounded up to whole milliseconds before the deadline is stored; this adds less than one millisecond and is not a wall-clock wait guarantee. Only explicitly retryable handler failures are retried, up to the configured attempt limit. Blocked tasks can be resumed with their observed state version after operators repair configuration.

## Execution and resource admission

The scheduler reserves requested CPU slots, GPU devices/labels, memory bytes, disk bytes, and custom integer units before the start CAS. A task whose resources are temporarily unavailable remains queued while later ready tasks are considered. By default, at most 32 successful newer starts may bypass an older resource-blocked task; `TaskExecutionServiceBuilder::max_resource_bypasses(NonZeroUsize)` changes this positive limit. Once the limit is reached, newer work waits for the older task even when unrelated resources are idle. The count is process-local and resets on restart. This policy is not strict FIFO and does not bound waiting time. Reservations count only after a successful start CAS and are released on every completion or failed admission path. They do not pin CPU cores, discover or isolate GPUs at the operating-system level, or enforce process memory/disk usage.

The task lifecycle uses `Queued`, `Running`, `Blocked`, `Succeeded`, `Failed`, `Panicked`, and `Cancelled`. State transitions compare the stored state version and attempt to reject stale writes. Queued or blocked tasks can be cancelled directly. A running task can be cancelled only according to its handler's declared mode: cooperative handlers observe `TaskContext::is_cancelled()` and must stop at a safe boundary; an external-hook handler delegates cancellation to its hook. Unsupported running cancellation is reported to the caller.

## Progress and history

Handlers report progress with `rs-progress::AsyncReporter` through their task context. `report_async()` waits for the progress snapshot to be persisted; subsequent task reads expose the current stage and metric values. Progress updates do not advance the task lifecycle state version. The reporter allocates each progress version before awaiting the store and never reuses it after a failed or cancelled report. An asynchronous store may commit before cancellation reaches its caller, so version gaps are valid; progress versions are independent of lifecycle `state_version`.

History pages sort ascending by `(accepted_at_ms, numeric task id)`. The exclusive `after` cursor contains that ordering key, not an offset. Each query observes its own store snapshot; concurrent inserts do not turn the cursor into a snapshot token. Filters include lifecycle state, `category`, and correlation key. `kind_id` is deliberately independent from category filtering.

## Reliability boundaries

SQLite persistence supports process restart recovery with at-least-once execution. A crash after an external side effect but before its result is stored can cause the handler to run again, so applications must make effects idempotent or protect them with their own transaction strategy. Scheduling is process-local; the crate does not provide distributed scheduling, forced interruption of arbitrary code, or exactly-once business effects.

Before persisting terminal-state diagnostics, the service limits `Failed.category` to 128 UTF-8 bytes and other terminal-state diagnostic fields to 4096 UTF-8 bytes. If text exceeds its limit, it keeps the longest UTF-8 prefix that fits with an appended `...`; direct `TaskStore` writes continue to reject over-limit diagnostics. External cancellation hook messages are bounded to 4096 UTF-8 bytes before the service returns or stores them; direct transitions with a longer `cancel_error` return `InvalidRequest`. Existing SQLite rows with longer hook diagnostics remain readable and are normalized on the next recovery or finalization write. Applications that need the full message should retain it in their own diagnostic system. With panic unwinding enabled, a panic from an application payload decoder while preparing a task is recorded as that task's `Panicked` outcome, and the service can continue dispatching later tasks. A panic from the handler future remains isolated to its task as before. `panic=abort` cannot be caught.

Store failures in background scheduling and finalization are latched. New writes stop, while diagnostic reads continue to use the store. The application must stop its own request or message intake before awaiting `shutdown()`; the crate does not control that ingress. Shutdown stops service admission and dispatch, waits for active handlers and cancellation hooks, drains the notification publisher up to its configured timeout, releases store ownership, and returns the shared result, including any stored failure. Queued tasks remain in the store for later recovery. Concurrent waiters observe the same release attempt; cancelling or timing out one waiter does not cancel the supervisor drain. A timeout does not establish that ownership is released, so retain the service handle and do not assume a replacement service can be built yet. A later explicit call retries a transient owner-release failure. If release panics, the supervisor resolves waiters with `StoreUnavailable` and hands the still-armed guard to the cleanup worker. Dropping the last external service handle requests the same drain asynchronously, but `Drop` does not wait or return an outcome. A handler or hook that never finishes can keep shutdown waiting indefinitely. A notification close error is returned after owner release succeeds; inspect durable outbox backlog for rows to be handled by a later service instance.

When configured with `TaskExecutionServiceBuilder::event_bus`, the service enables the store outbox and starts an asynchronous publisher after task recovery. Each lifecycle snapshot is inserted in the same SQLite transaction as its task transition. Until the provider reports acceptance, the row remains in the outbox and is retried; an uncertain result can therefore cause duplicate publication. Once the provider reports `Accepted`, the row is deleted. Acceptance does not prove persistence or consumer receipt: a Redis failure before persistence can lose a notification after deletion, and consumers are not guaranteed at-least-once delivery. This is distinct from the at-least-once task handler execution described above. This feature requires persistent outbox support; `MemoryTaskStore` rejects this configuration. Only transitions written while the outbox is enabled are captured; startup does not backfill older task states.

An unknown publish result or a crash after provider acceptance but before row deletion can cause the same snapshot to be published again. Consumers should deduplicate by `(TaskId, state_version)`, ignore stale versions, and call `get_state_checkpoint` after a gap. `None`, a query error, or a checkpoint older than the notification must not be ACKed; keep it on the Retry path. A checkpoint restores only current state and cannot replay each missing transition or its side effects. Because a lost tail notification may have no later event to reveal the gap, applications that need bounded convergence should durably track accepted task IDs and periodically reconcile bounded batches after an application-chosen staleness threshold. Query the checkpoint outside the consumer transaction, re-read the consumer version inside it, and write only when the authoritative version is higher. Keep tracking after query failure, `None`, or a stale checkpoint; retire an ID after its terminal projection commits. This repairs current state only and does not provide exactly-once processing. Monitor outbox row count and oldest-row age, and check Redis `XLEN` and `XPENDING` when Redis Streams is the provider. A failed outbox head can be inspected through `TaskExecutionService::notification_failure()` and explicitly archived with `quarantine_failed_notification(...)`; quarantine intentionally creates a notification gap and does not replay the archived row. See the [typed API guide](typed-task-api.md) and [user guide](user-guide.md#publish-lifecycle-changes) for usage and operational boundaries. Applications explicitly prune terminal history with bounded `TaskStore::prune_terminal_before`; SQLite skips tasks with active outbox rows and transactionally saves a terminal state checkpoint before deletion. Checkpoints have no automatic expiry and grow with pruned tasks. Pruning also releases idempotency keys for reuse, but SQLite reserves each pruned `TaskId` while its terminal checkpoint exists; `MemoryTaskStore` does not retain pruned identities.

Expected submit rejections (capacity, unfinished-task limit, idempotency conflict, and duplicate task ID) return structured request errors and do not latch the service. Other operational store failures retain the existing fault behavior. External cancellation hooks run in service-owned tasks: concurrent callers for one attempt share the hook, caller cancellation does not abort it, and `shutdown()` waits for it. A failed hook records a queryable diagnostic and can be retried by calling `cancel()` again while the task remains running. Hooks must be idempotent for (`TaskId`, attempt).
