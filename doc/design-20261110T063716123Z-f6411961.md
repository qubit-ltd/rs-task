## TASK-001：正延迟向上取整到毫秒

现状：`src/service/retry_policy.rs` 的构造器仅拒绝零初始延迟和上下界倒置；`src/service/typed_task_execution_service/internal/service_runner.rs:1111` 对 `delay_for_attempt` 的结果调用 `as_millis()`。因此 1ns 会变成零毫秒，1.5ms 会变成 1ms。

选择向上取整，不新增拒绝条件。拒绝亚毫秒配置会改变现有成功构造行为并增加错误分支；统一提高存储精度则需要 schema 与查询契约变化，均无必要。公开 `delay_for_attempt()` 继续返回原始 Duration；只在生成持久化期限时量化。

在 RetryPolicy 中增加 crate 私有的 `delay_millis_for_attempt(self, attempt: u32) -> u64`，先执行既有指数增长和封顶，再向上取整并饱和到 u64：

```rust
let delay = self.delay_for_attempt(attempt);
let millis = delay.as_millis() + u128::from(delay.subsec_nanos() % 1_000_000 != 0);
millis.min(u128::from(u64::MAX)) as u64
```

service_runner 使用 `now_ms().saturating_add(...)` 生成期限，保留现有时间戳饱和策略。Duration 最大值换算后的毫秒值远小于 u128 上限，计算加一不会溢出。

有效持久化间隔为 ceil(delay / 1ms)，小于一毫秒的正延迟至少为 1ms；相对策略返回值最多增加不足 1ms。max_delay 约束原始 Duration，量化后的间隔也可能高于 max_delay 不足 1ms，须明确记录。这是毫秒时间戳上的期限规则，不承诺实际墙钟等待至少原始 Duration，也不改变系统时钟调整风险。

测试覆盖 1ns、999999ns、1ms、1000001ns、封顶后取整、attempt=0、u32::MAX 和 Duration::MAX 的饱和边界。用可控制的存储记录 transition command，验证服务实际写入的 retry_not_before_ms 使用新转换；不使用亚毫秒 sleep 或依赖 CI 调度精度。原始 Duration API 的结果保持不变。

## TASK-002：终态检查点参与身份冲突检查

现状：`src/store/sqlite_task_store/internal/typed_store.rs:258` 只在 tasks 查重，清理逻辑在 `internal/prune.rs` 保留 task_terminal_checkpoints 后删除 tasks。重复 ID 可获得从零开始的新生命周期，`sqlite_task_store.rs:548` 又优先查询主任务，导致旧检查点被新身份遮蔽。消费者按 TaskId 和最高 state_version 去重时存在误忽略风险。

在 accept_encoded 原有事务内，将查重谓词扩展为两个 EXISTS：

```sql
SELECT EXISTS(SELECT 1 FROM tasks WHERE id=?1)
    OR EXISTS(SELECT 1 FROM task_terminal_checkpoints WHERE task_id=?1)
```

命中任一表均返回现有 `StoreError::DuplicateTask`；服务继续映射为 `TaskServiceError::DuplicateTaskId`，不锁存故障。不改变当前幂等键检查优先顺序：完全相同的已保留幂等请求仍返回既有记录。主任务表唯一键、事务和现有 owner 机制继续保持；不引入新的索引或 schema 迁移。

清理继续释放幂等键，但不释放 SQLite 已持久保存的任务身份。MemoryTaskStore 清理后不持久保留身份，维持现状；两类存储的身份保护期限应写清楚，应用始终负责生成跨重启唯一 ID。该防御不能修复已发生的身份复用，也不取代生成器正确配置，不自动删除既有冲突数据。

测试构造完成并清理的任务，以同 TaskId 提交不同请求，断言 DuplicateTask、主任务仍不存在、原检查点未变化。关闭重开数据库后重复断言。另测原幂等键配新 ID 可以受理，以及保留任务的相同幂等请求仍返回 created=false。启用 outbox 时验证拒绝不会新增通知行；服务层重复 ID 拒绝后仍能受理合法 ID。复用现有测试夹具与通知测试，不新增生产抽象。

兼容性：原先错误复用已清理 SQLite TaskId 的调用方将收到结构化拒绝；合法唯一 ID 调用方无需迁移。README 示例及下游 `rs-event-bus-redis/tests/fixtures/task_notifications/src/main.rs` 使用进程内计数器，其用途是示例/夹具，不能直接作为生产重启持久生成器。只补充说明，不改造下游业务架构。

## TASK-003：先测量，再引入预算快速路径

`src/store/memory_task_store.rs:257-274` 在同一互斥锁内无条件遍历终态队列并查询 BTreeMap，成本约 O(H log N)。即使无需回收也执行。不能据此认定现有业务已经出现延迟故障。

新增无额外依赖的 harness=false 基准 `benches/memory_accept.rs`，沿用现有基准组织方式。历史量取 0、256、4096、32768，每条 payload 固定 64 字节，预算设置为 64MiB，未完成上限保持默认。历史准备不计入计时；每批只计时不超过 128 次唯一请求受理，批间将新任务转为终态并清理至目标容量，避免未完成数超限及历史漂移。空历史组批间删除刚完成任务。测量至少 5 次重复，输出每组中位数、p95、样本数、构建模式和环境信息；不在 CI 使用绝对耗时阈值。

先保存当前源码基准报告，再尝试最小快速路径：若 `retained_payload_bytes.checked_add(requested_bytes)` 存在且不超过 max_payload_bytes，直接跳过 reclaimable_bytes 计算；否则执行原有回收可行性判断和驱逐流程。溢出视为需要慢路径，不能把溢出当作预算充足。不维护新计数器、不改变原有拒绝原子性和淘汰顺序。

对照测量使用同环境 release 构建。若大历史组改善超过重复样本波动、且空历史无可辨认回退，则保留快速路径；否则只保留测量证据与结论，不强行优化。测试验证预算充足、恰好满额、需要回收、不可回收拒绝且历史未变等外部契约，不为验证实现细节添加计数器接口。
