# rs-task 通知 outbox 故障恢复与可靠性表述设计

> 历史记录：主要设计已于 schema v7 实施，复选框是原计划快照；后续保留契约见[本设计](design-20261015T225508405Z-e5fffbbc.md)。

日期：2026-10-13
状态：已实施，历史设计
适用范围：`qubit-task` 的 `event-bus` + `sqlite` 组合，以及对应的中英文文档。

## 背景与目标

当前 publisher 按 `(created_at_ms, task_id, state_version)` 读取 SQLite outbox，并在一条记录发布失败时停止处理当前页。网络故障需要保留记录并重试；但 JSON 损坏、事件 ID 无法构造或持续无法编码的头部记录，也会让后续记录一直无法发布。现有 `notification_stats()` 只给出进程内计数，不能指出阻塞的是哪条记录；单条损坏快照的测试也没有覆盖后续正常记录的恢复。

另一问题是 README 和设计文档直接称通知投递为“至少一次”，但现有实现会在 provider 报告接纳后删除 SQLite outbox 行。Redis 接纳与持久化之间若发生故障，消费者仍可能收不到该通知。文档虽在后段说明了这个边界，首次表述仍容易被误解。

目标：保持默认的有序重试；让操作员能定位、审计并显式隔离阻塞记录，使后续通知恢复；在中英文文档中准确区分任务执行、到 provider 的发布尝试、provider 接纳及消费者收到事件这几个保证边界。

## 方案选择

| 方案 | 优点 | 代价与结论 |
| --- | --- | --- |
| 遇错自动跳过头部记录 | 后续事件立即恢复 | 会静默制造生命周期缺口，且无法判断总线故障是否暂时；不采用。 |
| 只暴露错误，要求停机后手工改库 | 改动少 | 操作缺少原子校验和审计，容易误删或与 publisher 竞争；不采用。 |
| 暴露失败头部并由操作员显式归档隔离 | 保留默认重试、顺序与证据，同时提供受控恢复路径 | 需要一张归档表和受 owner 保护的命令；采用。 |

隔离是明确的业务决策，不是“成功发布”。操作员须根据权威任务状态判断缺失通知的补偿方式；消费者仍按 `TaskId` 与 `state_version` 去重并在版本缺口时查询 service。

## API 与运行流程

在 `event-bus` feature 下新增 `NotificationFailure`，包含 `task_id: TaskId`、`state_version: u64`、`event_id: String`、`error: String`。`TaskExecutionService::notification_failure() -> Option<NotificationFailure>` 返回当前进程最近一次失败且仍位于 outbox 头部的快照；成功发布、隔离或头部变化后清空。该值是诊断快照，不是持久告警，也不代表 outbox 总量；重启后 publisher 再次读取失败记录时会重新形成快照。现有 `NotificationStats` 保持原有计数语义。

新增异步 `TaskExecutionService::quarantine_failed_notification(expected_task_id: TaskId, expected_state_version: u64, expected_event_id: &str, reason: &str) -> Result<(), TaskServiceError>`。只允许在已启用 publisher、服务未关闭、当前失败头部与全部期望值一致时调用；`reason` 去除首尾空白后须非空，UTF-8 字节数上限 4096。无失败头部、头部已改变或并发发布已成功时返回冲突；存储不支持该能力时返回明确的能力错误。该操作不会锁存整个任务服务故障，也不会将隔离计入 `published`。

调用经 publisher 的控制队列交给同一个 worker。worker 只在两次发布尝试之间处理命令；若调用发生在进行中的发布期间，等待该尝试结束，再重新校验头部。因此不会同时发布和隔离同一条记录。控制队列在失败退避期间可唤醒 worker；普通新任务通知不得绕过失败退避。关闭开始后拒绝新隔离命令；已接收的命令在释放 store owner 前结束，调用方取消等待不取消已接收命令。若 worker 异常退出，未完成的命令返回明确错误。

`TaskStore` 增加有默认 `UnsupportedCapability` 实现的隔离方法，避免强制所有自定义 store 实现。SQLite 实现须在同一事务和当前 owner fence 下：读取**当前最老** outbox 行；比较 `task_id`、`state_version`、`event_id`；将原始行连同操作时间、原因和当时的错误全文写入归档表；精确删除该行；提交。任一步失败均回滚。事务提交后 worker 清空失败快照、唤醒自身并继续从新头部处理。原始事件只保存在归档表，不自动补发、不重排后续事件。

`list_event_outbox()` 在读取键列之前出错时，当前接口可能无法构造 `TaskId`。本方案不尝试自动处理损坏的键、缺失表或结构异常；这些仍返回存储故障，须在停机并备份后修库。可隔离范围是**可读取键列、但发布过程持续失败**的记录，包括无效 JSON、无效 `EventId`、请求构造/编码失败及 provider 拒绝。允许操作员隔离 provider 失败的记录是有意的：只有显式传入头部身份和原因才能丢失该次通知。

## SQLite schema 与迁移

将 typed SQLite schema 从 v6 提升到 v7。新增 `task_event_outbox_quarantine` 表：保留 `task_id`、`state_version`、`event_id`、`event_json`、`created_at_ms` 原值，并增加 `quarantined_at_ms`、`reason`、`last_error`；以 `(task_id, state_version)` 为主键。归档表不对 `tasks` 设置级联外键，避免清理终态历史时销毁审计记录。归档记录不会由 `prune_terminal_before` 自动清理；保留期限由应用的数据库治理决定。

`SqliteTaskStore::open` 在一个事务中支持新库及既有 typed v4、v5、v6 到 v7 的升级，保留已有任务和未投递 outbox 行。对旧 UUID schema 仍明确拒绝且不改动。v7 重开时验证两张 outbox 表的必需列和索引；若升级或验证失败，事务回滚并保留原数据。实现时须调整当前依赖 `version != NEXT_SCHEMA_VERSION` 创建 outbox 表的分支，避免 v6→v7 重复创建已有表。此计划不改 `Cargo.toml` 的 crate 版本；发布版本由后续发布流程确定。

## 可靠性契约与文档

准确表述为：SQLite 任务状态和 outbox 记录在同一事务中提交；在 provider 确认接纳前，publisher 保留记录并可重试，因此可能重复发布；确认接纳后删除 outbox 行。`Accepted` 不保证磁盘持久化、复制或消费者处理，因此**不能承诺通知到消费者的至少一次送达**。任务 handler 的重启恢复仍是独立的至少一次执行语义。隔离记录会有意形成通知缺口，归档只保存证据，消费者应查询 service 的当前权威状态。

同步修订 `README.md`、`README.zh_CN.md`、两份设计文档、两份用户指南及两份当前迁移指南。首次出现通知可靠性描述时即写清上述边界；用户指南提供失败身份查询、核对、显式隔离、归档检查及版本缺口补偿的操作顺序，并注明 schema v7 和隔离属于有意丢失单条通知。保持中英文含义一致；历史 0.8 迁移说明不改。

## 验证与验收

1. 存储测试：v4/v5/v6→v7 及重开保留任务和 outbox；归档与删除原子化；错误身份、非头部、无 owner、重复命令、故障注入均不丢行；归档在终态清理后仍存在。
2. Publisher 测试：坏 JSON 头部挡住正常后续行；诊断给出正确身份；显式隔离后后续行发布；普通 provider 暂时失败只重试；在发布成功竞态中隔离返回冲突且不归档；取消等待和关闭不会使命令半完成。
3. 文档测试：现有可编译示例继续通过；中英文 README、设计、用户指南和迁移指南在保证边界、schema 版本及操作顺序上逐项一致。
4. 集成门禁：`cargo test --locked --all-features`、`cargo test --locked --no-default-features`、`cargo doc --locked --all-features --no-deps`，以及项目现有 CI 检查。需要 Redis 的现有集成测试按仓库要求提供服务；缺少外部 Redis 时明确记录未运行项，不能宣称全量通过。

## 范围边界

本设计不改变任务调度或 handler 的重试策略，不自动跳过任何 outbox 行，不承诺 Redis 接纳后的持久性，也不提供归档记录的自动重放。下游 `rs-event-bus-redis` 的任务通知 fixture 用于核对现有公开 API 接入；新增 API 不要求它立即迁移。
